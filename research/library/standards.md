ISO 9241 は「Ergonomics of human-system interaction」のシリーズである。ソフトウェアの使いやすさと人間中心設計に関係する代表パートだけを置いた。本文は購入が必要で、この作業では規格本文を読んでいない。ISO のカタログページはボット検証で本文が取れなかった。以下の書誌と抄録は、ISO または ANSI の公開カタログ、および 9241-112 の公開サンプルに依る。原理の箇条を記憶で補わない。

## Web Content Accessibility Guidelines (WCAG) 2.2

| 項目 | 内容 |
| --- | --- |
| 種別 | 現行の公式資料 |
| 著者/組織 | W3C Accessibility Guidelines Working Group。編集者は Alastair Campbell、Chuck Adams、Rachael Bradley Montgomery、Michael Cooper、Andrew Kirkpatrick |
| 年 | 2024-12-12 付の W3C Recommendation（2.1 は 2018、2.0 はそれ以前） |
| 分野 | アクセシビリティ |
| 無料で読めるか | 無料。W3C の技術報告書 |
| 優先度 | 高。編集メモであり、Core の推奨値ではない |
| URL | https://www.w3.org/TR/WCAG22/ |

### 何について書かれているか

今回開いた勧告の概要と序論による。WCAG 2.2 は、ウェブコンテンツをよりアクセシブルにするための推奨である。対象には、視覚、聴覚、身体、発話、光感受性、それらの組み合わせ、学習障害と認知的制約の一部が含まれる。すべてのニーズを満たすとは書いていない。デスクトップ、ラップトップ、キオスク、モバイルを含む装置上のウェブコンテンツが対象で、従うと一般の利用者にも使いやすくなることが多い、と概要にある。

ガイダンスは四層である。原則は perceivable、operable、understandable、robust の四つ。その下に 13 のガイドライン、試験できる達成基準、十分な技法と助言的技法がある。適合レベルは A、AA、AAA。AAA でも、とくに認知・言語・学習の領域ではすべての人に届かない、と序論は書く。

2.2 に適合するコンテンツは 2.1 と 2.0 にも適合する、と本文にある。2.0 と 2.1 は廃止されていない。W3C は、方針が古い版を指していても、将来のために 2.2 を使うよう勧めている。2.2 で削除された達成基準は 4.1.1 Parsing である。新しく加わった達成基準の名前は、Focus Not Obscured（Minimum / Enhanced）、Focus Appearance、Dragging Movements、Target Size (Minimum)、Consistent Help、Redundant Entry、Accessible Authentication（Minimum / Enhanced）である。各基準の閾値は、この項目では写さない。部品を作るときは該当する達成基準の本文を開く。

支援文書として、How to Meet WCAG 2.2、Understanding WCAG 2.2、Techniques がある。技法は参考であり、達成基準そのものではない。後続の大改訂（勧告本文は WCAG 3 という名前をここで使っていない）は別作業で、2.2 はそれまでの更新だ、と「Later Versions」にある。

日本語で読むなら [WAIC の翻訳](#wcag-22-ja)。日本の購入規格は [JIS X 8341-3:2016](#jis-x-8341-3) で、一致しているのは WCAG 2.0 である。

### UIデザインシステムとの関連

コンポーネントの名前、役割、値、キーボード、フォーカスの見え、ターゲットの大きさ、コントラスト、動き、エラー回復を、見た目の好みとは別に試験できる。達成基準の数値（コントラスト比やターゲットサイズ）は WCAG の要求であり、andm の radius や spacing のスケールではない。写すなら、どの達成基準のどの文から採ったかを分析側に残し、このライブラリには再掲しない。

### なぜ読む価値があるか

アクセシビリティをデザインシステムの品質ではなく、適合として扱える現行の勧告だからである。Understanding を併読しないと、達成基準の意図を技法の一例と取り違える。

### 確認

確認済み。2024-12-12 の勧告ページを開き、概要、状態、序論、2.1 との差分に名前が出ている新しい達成基準まで読んだ。達成基準の本文すべてをこのカードに要約してはいない。

## Accessible Rich Internet Applications (WAI-ARIA) 1.2

| 項目 | 内容 |
| --- | --- |
| 種別 | 現行の公式資料 |
| 著者/組織 | W3C Accessible Rich Internet Applications Working Group |
| 年 | 2023-06-06 の W3C Recommendation。1.3 は別の Working Draft |
| 分野 | アクセシビリティ、UI の意味 |
| 無料で読めるか | 無料 |
| 優先度 | 高。編集メモであり、Core の推奨値ではない |
| URL | https://www.w3.org/TR/wai-aria-1.2/ |

概説: https://www.w3.org/WAI/standards-guidelines/aria/

### 何について書かれているか

W3C の概説ページを開いた。WAI-ARIA は、動的なコンテンツと、HTML と JavaScript で作る進んだ UI を、支援技術が伝えられるようにする一式である。ロール（menu、treeitem、slider、progressbar など）、ページ構造のロール、状態（checked、readonly など）、ライブリージョン、キーボード操作の意味を文書に足す。仕様本文は主にブラウザ、支援技術、評価ツールの実装者向けで、著者がウィジェットをどう組むかは Authoring Practices 側が担う、と概説は分けている。

1.2 は 2023-06-06 の Recommendation である。同じ概説は、1.3 は草案で、suggestion、comment、mark などのロールや、aria-description などが提案に含まれる、と書いている。1.3 の Working Draft（2026-06-04 付を検索で確認）は勧告ではない。部品の実装が従う現行の勧告は 1.2 である。

関連する勧告として、概説は Core Accessibility API Mappings 1.2、Accessible Name and Description Computation 1.2、HTML と SVG のマッピングを挙げている。名前の計算は、可視ラベルとアクセシブルネームがずれる事故を読むときに別途開く。

### UIデザインシステムとの関連

ボタン、タブ、ダイアログ、メニューを div で再実装するとき、ロールと状態とキーボードが仕様の問題になる。見た目のトークンでは代替できない。著者向けの手順は次の APG を開く。ARIA を足す前に、ネイティブの HTML 要素で足りるかを先に見る。

### なぜ読む価値があるか

カスタムコンポーネントが「見た目はボタンだが、支援技術にはただの箱」になるのを避けるための意味の語彙がここにある。1.3 の草案を現行の契約条件と取り違えないためにも、勧告の版を固定して参照する。

### 確認

確認済み。概説ページと、1.2 勧告の状態表示を開いた。ロール定義の全文は読んでいない。1.3 は Working Draft の状態を確認し、本文の差分はカードに写していない。

## Design Tokens Format Module 2025.10

| 項目 | 内容 |
| --- | --- |
| 種別 | 現行の公式資料（Community Group の報告書。W3C 勧告ではない） |
| 著者/組織 | W3C Design Tokens Community Group |
| 年 | 2025-10-28 の Final Community Group Report |
| 分野 | デザイントークン、ツール間の交換 |
| 無料で読めるか | 無料 |
| 優先度 | 高。編集メモであり、Core の推奨値ではない |
| URL | https://www.designtokens.org/TR/2025.10/format/ |

報告書の告知: https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/

### 何について書かれているか

仕様の導入までを読んだ。デザイントークンを、分野とツールと技術をまたいで設計判断を表す方法だとし、人間が読める名前と値の組を最小単位とする。色やサイズをデザインツールが名前で参照し、変換ツールがプラットフォーム別のコードにし、文書ツールが生値ではなく名前を見せる、という流れを相互運用するためのファイル形式である。形式は JSON で、トークンの型、グループ、別名参照を定義する。導入が例に挙げる型は color、size、duration である。

状態欄は、これは W3C 標準ではなく、W3C の標準化トラックにも載っていない、と明記している。Community Group として安定版であり、実装されることを意図している、とも書く。仕様中の色や寸法の例は、形式の説明であり、andm が採用すべき値ではない。

### UIデザインシステムとの関連

トークンをどうファイルにし、ツール間で受け渡すかの形式である。どの色が正しいか、どの余白が正しいかは規定しない。Core の値をこの仕様の例から採らない。名前の設計（何をトークンにするか）は、別の判断である。

### なぜ読む価値があるか

「トークン」が色の表の別名で終わらないよう、交換形式として何が安定したかを確認できるからである。勧告ではないので、WCAG と同じ拘束力だとは扱わない。

### 確認

確認済み。2025.10 の Format Module の状態、導入、用語（トークン、プロパティ、型、グループ）を読んだ。型ごとの文法の全文は通読していない。

### 何について書かれているか

個別コントロールの提案本文はこの作業では通読していない。

### UIデザインシステムとの関連

ボタンやセレクトを自作するとき、ネイティブコントロールがどの部分と状態を持つかを、ベンダーの見た目と分離して参照できる。andm の見た目トークンの正本ではない。

コンポーネントを「自社の見た目」だけで定義すると、プラットフォームが既に持つ状態を落とす。Open UI はその解剖を標準化しようとする現在の作業場である。

### 確認

| 項目 | 内容 |
| --- | --- |
| 種別 | 現行の公式資料（Nielsen Norman Group が維持する記事。国家規格や W3C 勧告ではない） |
| 著者/組織 | Jakob Nielsen。記事の更新に Kate Moran、Feifei Liu。視覚は Kelley Gordon |
| 年 | ヒューリスティックの改訂は 1994。記事の最終レビュー表示は 2024-01-30。初出は Molich との 1990 年の仕事、と記事が書いている |
| 分野 | インタラクションデザイン、ヒューリスティック評価 |
| 無料で読めるか | 記事は無料。1994 年の論文と書籍の章は別途、出版社経由 |
| 優先度 | 高。編集メモであり、Core の推奨値ではない |

### 何について書かれているか

記事を開いた。10 項目は経験則であり、細かいユーザビリティ指針ではない、と冒頭にある。項目は、システム状態の可視性、システムと実世界の一致、利用者の制御と自由、一貫性と標準、エラーの防止、想起より認識、柔軟性と効率、美的で最小限のデザイン、エラーからの回復、ヘルプと文書である。

Nielsen の注によると、1990 年に Molich と作り、1994 年に 249 のユーザビリティ問題の因子分析から説明力が高い集合へ改訂した。2020 年に説明と例を足したが、10 項目自体は 1994 年から変わっていない、と記事は書く。

第8項は、関係の薄い情報が増えると、必要な情報の相対的な見えが落ちる、という主張で、フラットデザインを強制する意味ではない、と記事が明示している。第6項は短期の記憶が限られるので、認識できる方が負荷が小さい、と説明する。これは Miller の論文の数値をメニュー個数に変換する話ではない。

部品の状態が見えるか、取り消しがあるか、同じ言葉が同じ行為か、エラーを事前に防ぐか、をレビューするときの公開チェックリストである。美的最小限を、特定の余白や角の値だと読まない。

### なぜ読む価値があるか

今も更新されている短い正本で、ヒューリスティック評価の共通言語になる。規格ではないので、WCAG の適合と混ぜない。
