# 出典優先設計（Source-First Design）

2026-10-08 採用。andm-ui 内の設計方針名であり、学問名ではない。各 Series の元となる公式デザインシステムを最優先し、確認した範囲で定義が足りない部分だけを補完する。公式仕様の置換や、全 Series の平均化は行わない。

## 判断の順序

| 順序 | 読むもの | 採用する範囲 |
| --- | --- | --- |
| 1 | 対象 Series・版・プラットフォームの公式コンポーネント仕様、トークン、ガイドライン | 明示された値・意味・状態・振る舞い。用途制約、非推奨も含む |
| 2 | 同じ公式システムの基礎尺度と関連部品 | 未定義部分を同じ言語で導出する。対応付け・換算・類推は `derived` として記録 |
| 3 | 適用範囲を確認した標準、学術資料、専門資料 | 公式で不足するグルーピング、階層、操作などの判断を補完。実験値を CSS 値に転記しない |
| 4 | andm の設計判断と検証 | 根拠の届かない数値・表現は `andm-original`。理由と限界を記録 |

この順序は見た目と Series 固有の仕様についての優先順位である。Native HTML の意味、操作と ARIA の一致、適用するアクセシビリティ要求は並行して確認する。公式仕様と衝突した場合は、適用条件を調べ、必要な差分を記録する。差分を「公式準拠」と表示しない。

他社システムは比較資料に使えても、対象 Series の穴埋め値の供給元にはしない。Baseline を継承する場合も、その値の根拠を継承するだけで対象 Series の公式値にはならない。andm 独自 Series は外部の公式再現とせず、目的・採用した尺度・設計判断を正本とする。

## 「定義がない」と「未確認」を分ける

確認状態はプロパティ単位で記録する。ページを一つ開いたことを Series 全体の確認に拡張しない。

| `sourceStatus` | 意味 | 次の行動 |
| --- | --- | --- |
| `specified` | 対象範囲の本文に仕様が明示されている | 仕様を採用するか、差分を記録する |
| `not-specified-in-checked-scope` | 関連仕様・基礎資料の本文を確認したが、その範囲に当該定義がない | 確認した URL・節・版を列挙して補完を検討する |
| `unverified` | 未読、取得失敗、JS 必須、タイトル・抄録だけ、版や対象が不明 | 取得・対象の確認を先に試す。欠落とは断定しない |
| `not-applicable` | 外部公式のない独自 Series、または対象外の仕様 | andm の判断・対象外の理由を記録する |

公式システム全体に定義が存在しないことを、一部ページの不在から断定しない。「公式値なし」という旧記録は、その確認範囲を照合してから分類し直す。本文未取得なら `unverified`。

未確認でも実装を進める必要がある場合は、既存の値を維持するか暫定の独自値を使う。`sourceStatus: unverified`、暫定理由、再確認先を残す。これを「公式の欠落を研究で補完済み」と扱わない。

## 根拠の分類

`basis`（実装判断の根拠）と `sourceStatus`（対象公式の確認状態）は別の軸である。部品全体に一つの「公式」ラベルを付けず、色、寸法、文字、構造、操作、動きなどを分ける。

| `basis` | 意味 |
| --- | --- |
| `official` | 読めた一次資料が、その対象・単位・状態の仕様を明示する。資料の権威を `series` / `standard` 等で明記 |
| `derived` | 確認済みの対象 Series の仕様から、役割への割当・換算・計算・類推を行った。元仕様と導出を両方残す |
| `research-based` | 本文を確認した学術・専門資料の原則を、未定義部分の設計判断へ適用した。UI への適用は andm の解釈 |
| `andm-original` | 独自の値・構造・表現・既定。Baseline の継承や暫定値も該当 |
| `unverified` | 実装値そのものの出典・導出をまだ確認できない。既存実装の未監査項目等 |

例えば、Apple の本文を取得できず Baseline の本文サイズを使う場合、実装値は `andm-original`、Apple の確認状態は `unverified` となる。標準に明示された操作要求を採用しても、Apple 由来の `official` にはならない。公式の数値を andm の用途に割り当てる場合は、数値の引用と用途への `derived` 判断を分ける。

## 補完の実務手順

1. 対象を固定する。Series、版、プラットフォーム、部品、プロパティ、状態、単位、密度を記録する。
2. `research/analysis/`、該当部品の出典文書、責務 README を読み、公式の該当仕様・関連する基礎資料の本文を確認する。既存メモを読むことと今回の再取得を分ける。
3. 仕様がある部分は優先する。足りない部分は同じ Series の尺度・類似部品から導出できるか検討する。Button の寸法を別部品の公式値と呼ばない。
4. 確認範囲に定義がない場合だけ、[文献索引](../research/library/README.md)から該当する根拠を選び、本文・適用条件・限界を確認する。書籍名の列挙だけで採用しない。
5. 原則からの判断と実装値を分ける。値は対象 Series の尺度から選び、選択理由を残す。尺度も未確認なら暫定独自値として記録する。
6. [判断記録](SOURCE-DECISIONS.md)に、下の形式で変更対象の根拠を残す。未決の提案は `recommended: null`。明示の実装依頼がある範囲はその依頼を採用根拠として進め、毎回の再承認は求めない。
7. CSS-first / Token remapping を維持して実装する。変更した状態・日本語・狭幅・文字拡大・キー操作・Series 差分を確認し、実測・目視・未検証を区別する。

## 余白・視覚的階層・群化への適用

先に情報の関係を定め、次に対象 Series の公式尺度へ対応付ける。次の名前は設計判断の意味ラベルであり、実装済み CSS Token の一覧ではない。

| 意味ラベル | 関係 | 確認すること |
| --- | --- | --- |
| `spacing.related` | ラベル・入力・補足など強く結びつく要素 | 別項目より同じ項目との関係が読み取れるか |
| `spacing.group` | 同一グループの項目 | 同じ役割が揃い、項目間の区別も保てるか |
| `spacing.section` | 異なる情報群 | 見出し、距離、境界、背景が一貫した区切りを示すか |
| `spacing.region` | ナビ・本文など大きな領域 | 領域の役割と読む順序を識別できるか |

4 / 12 / 24 / 48px のような共通値や一定比率は規定しない。近接、類似、連続などの手がかりは競合もするため、距離だけで自動合否を決めない。余白を広げる Series と境界・背景で分ける Series の両方を許容し、ラベルの所属、情報の階層、主要操作の意味を保つ。

近接と類似の出発点は [Wertheimer の英訳](../research/library/academic.md#wertheimer-1923)。専門的な UI への解説は [NN/g: Proximity](https://www.nngroup.com/articles/gestalt-proximity/) と [Visual Design](https://www.nngroup.com/articles/principles-visual-design/)。学術論文と専門解説は区別する。これらは特定の CSS 余白値の公式根拠にはならない。2026-10-08 に公開本文を確認。

新しい意味 Token は再利用される責務が必要になったときだけ追加する。この方針の採用だけで全 Series の数値を一括変更しない。

## 記録形式

新規・変更分は下記を埋める。複数の根拠がある場合はプロパティや判断を分け、共通根拠は記録 ID を参照できる。同じ記録を複数箇所へ複製しない。

```yaml
id: <安定した判断ID>
series: <Series名>
target: <部品 / Token / プロパティ / 状態>
implementation: <コードパス、セレクタ、Token名>
scope: <版、プラットフォーム、密度、単位>
sourceStatus: <specified | not-specified-in-checked-scope | unverified | not-applicable>
checkedScope: <確認した公式仕様と基礎資料、取得結果>
basis: <official | derived | research-based | andm-original | unverified>
sources:
  - authority: <series | standard | academic | professional | andm>
    locator: <一次URL / DOI / 書誌 / リポジトリのパスと節>
    version: <版 / タグ / commit / 継続更新 / 未確認>
    checkedAt: <実際の本文確認日。不明・未取得なら null>
    verification: <本文確認 | 一部確認 | 既存記録のみ | 未確認>
    supports: <何を裏付けるか。値と原則を区別>
decision: <採用値・対応付け・補完方法・根拠の届く範囲>
alternatives: <同じSeriesの候補と不採用理由>
recommended: <採用なら true、不採用なら false、未決なら null>
adoption: <ユーザー依頼 / 既存採用の維持 / 提案中>
validation: <条件、確認結果、未検証>
revisit: <再確認先と見直しを起こす条件>
```

旧記録は保持する。全プロパティの監査・移行は未完了であり、記録がない値を新ルールだけで確認済みにしない。

## 更新時の見直し

公式の版・該当仕様の更新、本文の取得成功、プラットフォーム変更、検証の不具合が契機になる。記録の `sources` と `implementation` から影響箇所を特定し、補完値と新公式仕様を比較する。採用する場合はコード、出典記録、検証結果を一緒に更新し、旧判断の理由は履歴に残す。既存の類推・換算・未確認値を自動的に `official` へ昇格させない。

現時点では人と AI の実装手順であり、公式更新の自動監視・自動補完・全値の追跡ツールは未実装。Research は Build 外・Runtime 非依存のまま、採用した判断のみを明示的に Spec / Token / CSS に反映する。
